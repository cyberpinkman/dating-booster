## 重复工作的来源

原 `ManagedRun` 每个 tick 都调用 `scan_message_list`，但只选择一个对象。
TaShuo 每次扫描都准备消息页、获取截图、调用列表视觉模型；一个列表里有 N 个
待处理对象，处理它们可能分析同一个列表 N 次。此外，单个对象返回 wait 会使
整个前台循环等待 poll interval，即使其他对象仍在等待处理。

这是代码中可复现的工作量放大机制，不能单独解释某次实机测试的全部耗时。
视觉服务、生成服务、窗口捕获、OCR/Accessibility、页面稳定等待均可能贡献延迟。
当前改动没有把这些操作的耗时假定为零，也没有实机速度倍数承诺。

## 一轮发现，逐个重新核对

TaShuo live provider 启用最多 120 秒的进程内待处理队列。队列在扫描开始时计龄，
每个候选只消费一次；耗尽或过期后重新扫描。其他 provider 默认保持逐 tick 扫描。
队列只保存发现线索，不能充当发送证据，也不跨进程恢复。

打开对象时，原有 adapter 仍返回消息列表，并在新截图中按视觉锚点重新定位行；
会话读取、目标绑定、权威 inbound revision、去重和四段发送验证照常执行。
某个对象等待或需要用户处理时，当前批次的其他对象可立即继续。
暂停/恢复、终止、状态变化以及发送结果未知会丢弃队列。

视觉模型可能把名字配到错误行坐标。视觉解析候选后，真实 Mac session 复用原
截图调用一次 Apple Vision accurate 中文/英文文字识别，以实际文字 bbox 校准
点击位置与视觉锚点。完整名字唯一匹配直接校准，重复匹配则跳过。完整匹配失败
时，对同页未定位候选共享一次视觉请求，只能从原生文字框编号中选择昵称锚点；
代码计算实际坐标，保留完整昵称，不做模糊匹配或删除 emoji。选框不确定、冲突、
响应格式不合法的候选跳过，不继续使用猜测坐标。没有逐行重试或模型定位循环，
进入线程后仍核对目标身份。识别请求不
提供预期昵称或自定义词典，结果不作为聊天正文或发送结果证据。Jev 不参与像素定位。

不提供原生 OCR 接口的兼容 session 保留原 Tesseract TSV 接口及一次稀疏版面
补充；真实 Mac 路径不在原生识别后叠加这两次调用。识别不可用时保留视觉路径，
不降低身份要求。以下局部计时不能代表端到端耗时或成功率。

后续定位确认：旧固定网格校正会覆盖视觉返回的坐标和 bbox，尤其在 emoji 名字
无法被 OCR 匹配时可能点到相邻行。现已删除该校正与合成行 fallback；依据真实
视觉 bbox 中心派生 tap 仍有效，不再用假定行距替换已观察到的位置。

Host 应持有同一个 `manage run --wait` 进程。逐个从外部调用 `manage tick`
会重建运行时，无法复用进程内队列；逐次由 Codex 读图、分析、点按也不是这条热路径。

## 2–3 条短消息连续发送

原 writer 已能生成 `message_sequence`，但 ManagedRun decision adapter 只提取
`best_reply`，序列没有进入发送层。旧兼容 executor 虽有循环，遇到视觉待确认会
返回 host；原先启动的连续窗口仍在计时。旧 AX conversation revision 包含全部
可见 static text，自己发出的气泡也会改变哈希，不能直接重复使用旧绑定。
这些是可复现的代码机制；没有读取历史实机日志来认定某次十几分钟间隔的唯一原因。

当前 ManagedRun 保留 writer 一次起草、通过 policy 的完整 2–3 条消息，先持久化
整组，再在同一个 tick 内顺序执行。Jev 判断、起草和内容检查全部发生在第一条前，
组内不重复 Jev 分流、起草、列表扫描、host 往返或轮询等待，仍保留视觉验证。
单条自然回复仍可只发一条，
不会按标点机械拆开；超过 3 条或无效序列会 handoff，不截去尾部。

句末标点和不足四字的气泡不能单独证明“机械拆句”。这类启发式保留为内部自然度
建议，不再因此禁止整组发送；内容、事实来源、授权和策略边界仍独立检查。

每条都经过 exact stage、Return 前目标/会话/文本复核、独立 checkpoint 和新鲜
post-send 验证。默认 AX 负责输入框空白检查、精确读写及发送后清空确认；视觉
负责目标、正文及发送后新增气泡的完整原文核对，不要求 AX 暴露聊天正文。

初始验证复用已读取会话的截图。在窗口与输入框几何可核对时，屏蔽真实输入框及
下方工具栏后，未变的聊天区像素走本地快路；需要视觉判断时，同一进程在一次
请求中按顺序提交前后两图，无需 Codex 逐条读图往返。不能凭固定裁剪坐标、任意
AX 标签或“出现了一个气泡”推断发送成功。

首次输入框聚焦已移到会话基线截图之前，避免起草后才聚焦所引起的通知横幅变化
触发会话变化阻断。

正常每条消息只采集写入前、Return 前和 Return 后三张新截图；原子 AX 写入的
精确读回结果直接作为 staging 证据，不再为同一件事重复截图、读取和调用模型。
输入框只缓存经过验证的 AX 元素索引路径，路径失效时重新发现；内容、焦点、
前台状态和窗口几何每次实时读取。已聚焦时不再点击输入框，截图热路径不再重复
运行 doctor、激活应用和查询窗口。

只有目标及预期新增气泡得到验证后，才更新下一条的视觉基线；逻辑 inbound
revision 保持不变，用于去重。若同时出现新来信且本条已确认，本条计为已发，
剩余消息取消，随后重新观察；不能继续发送旧组尾部。Return 后结果未知时暂停
整个 run，禁止自动重试。明确证明未执行 Return 的阻断记为 `failed_before_click`，
释放本次预留预算；普通点击异常仍按 `unknown_after_click` 保留预算。

未知发送结果同时阻断 start/resume，返回
`unknown_after_click_requires_reconciliation`；旧版遗留的 active 状态也会在触碰
GUI 前暂停。不能通过 stop/start 或候选标识变化绕过核对，也不能删除记录来继续发送。
使用下述 `manage reconcile` 只核对已有发送证据，不重发。

连续窗口从实际发送开始；慢速起草和第一条 staging 不占用它。后续每次 Return
前检查距上次发送不超过 20 秒，后续 staging/GUI 延迟也计入。此限制阻止迟到的
旧气泡，不保证不可靠的 App/AX 能在 20 秒内完成。若在 staging 后超时，已放入
输入框的草稿可能仍需处理，不能把取消或暂停报告成整组成功。

每个气泡独立消耗发送预算。整组内容和逐条进度保存在既有加密状态中；审计只记录
标识、hash、数量和原因。进程中断后的未完成尾部不自动续发，也不重发已确认的
消息；未知点击结果仍走原有恢复暂停机制。策略检查同时检查逐条内容与完整正文，
不能靠拆开“明晚八点 / 我们见面吧”绕过具体邀约 handoff。

## 未知结果的证据恢复

```bash
dating-boost manage reconcile --data-dir .local/dating-boost --run-id <run_id> --json
```

默认选择唯一未核销尝试；有多个时用 `--decision-key` 指定。命令仅调用证据恢复
端口，核对原回执、目标、点击时间、精确正文及证据摘要，不 stage、不按 Return，
也不恢复旧消息组尾部。不接受人工 success 布尔或裸 expected text。证据不足时
保留 unknown；核验成功则另存幂等核销记录，原 unknown 尝试和审计仍保留，发送
预算不退款，确认计数仅增加一次。旧 run 仍为 stopped/paused，不自动启动；
paused run 在明确 resume 后，host 还须为同一 run 重新持有 `run --wait`。

新的发送路径把原始 pre/receipt/post 摘要和关联写入加密持久化证据，恢复时仍
校验原截图内容。对本次 legacy 记录，只能由 host 审核原工具捕获与回执的关联，
明确记录导入 provenance，再走证据验证；不能声称它在原发送时已有 manifest。

表情补充验证范围很窄：普通正文必须完全一致，差异仅限最多三个
U+1F600–U+1F64F 范围内的表情；AX 已精确确认输入，前后双图已确认同会话新增
outbound。再额外进行一次“前图输入框与后图新增气泡”的可见内容比较，不向模型
提供 expected 字符串；只有两处都完整可读、结果 `identical` 且置信度 `high`
才可作为组合证据。每对 frame 的 verdict 都持久化，包括否定和不确定结果，
不能反复请求直到取得肯定结果。这不把不同 emoji 定义为相同 Unicode，也不能
推广为模糊文本匹配。该组合证据已用于一次旧 run 的核销；新的连续实发仍待验收。

## 可选 Jev 分流

按 [TypeSafe 的编程模型](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)
拆分职责：代码调度，Jev 作有限选项判断，现有生成模型起草，原有安全层决定能否执行。
Jev 接收文本/JSON，不作为图像识别或回复生成 backend。官方[模型说明](https://docs.typesafe.ai/models)
指出当前模型英语表现最好，中文判断效果需要单独评估。

用环境变量显式启用：

```bash
export TYPESAFE_API_KEY="<your-typesafe-key>"
export DATING_BOOST_MANAGED_RUN_JEV=1
```

不需要额外 SDK。实现直接调用官方 [HTTP API](https://docs.typesafe.ai/api)
`POST https://api.typesafe.ai/v1/systemone`，默认模型 `jev-latest`。
只存在 key 不会隐式启用服务。启用但缺少 key 时，在 GUI 和模型初始化之前返回阻断原因。
环境变量设置到持有前台 run 的同一进程；不会从其他项目复制密钥。

高级 provider JSON 可在原有 `app_id`、`runtime`、`backend`、`vision_backend`
配置旁增加：

```json
{
  "semantic_router": {
    "type": "typesafe",
    "model": "jev-latest",
    "api_key_env": "TYPESAFE_API_KEY",
    "timeout_seconds": 5,
    "confidence_threshold": 0.85,
    "probability_threshold": 0.90
  }
}
```

`semantic_router: {"type": "disabled"}` 显式关闭，优先于环境开关。
模型 alias 会随供应商更新，需要固定版本时按官方模型列表配置 model。

同一个请求同时询问两个独立 Choice：

- `boundary`：普通聊天、用户接手、不确定。
- `response_need`：值得回复、明确可以等待、不确定。

高置信度的用户接手直接 handoff；高置信度普通聊天且明确无需回复直接 wait。
接手分支不依赖另一个推测性问题的答案。需要回复、上下文不足、置信度不足或服务
失败均回到现有 planner，保留生成后的确定性策略检查。Jev 的“普通聊天”判断
不是授权证明，不会越过 nudge、目标核对、staged text 或 post-send gate。

请求只包含当前可见消息的 sender/text 和最新 inbound 文本，不包含截图、昵称、
资料、记忆库、文件路径或授权对象。输入超出界限或观察置信度低时回退，不截去
关键上下文后直接判定。响应校验包括问题 ID、类型、选项、概率范围和分布。

默认单次网络 timeout 为 5 秒，不自动重试；服务失败后 30 秒内跳过分流，
防止每个对象重复支付失败等待。此 timeout 是 HTTP I/O 超时，不是所有 DNS/TLS/
慢速流式返回情况下的硬性整轮时限。0.85/0.90 是可调整的初始阈值，尚未经真实
中文 dating 数据校准。所有对象都需要回复时，Jev 会增加一次请求；收益取决于
能跳过多少无效起草，应根据计时与标注样本评估。

## 验证与测量

```bash
python3 scripts/managed_run_benchmark.py
python3 -m pytest tests/test_managed_run.py tests/test_managed_run_provider.py tests/test_typesafe.py tests/test_managed_triage.py tests/test_tashuo_managed_live_action.py -q
```

基准使用合成会话和内存状态，对比扫描、会话读取、起草、语义请求及安全验证次数。
它不打开 App，不发消息，不调用真实模型服务；结果代表控制流工作量，不代表实机
延迟或中文判断准确率。
另外覆盖 2/3 条消息、Jev 开/关四种连发场景：使用虚拟时钟模拟 180 秒规划，
检查组内不重复语义分流/起草、每条验证连续执行、消息顺序完整保留。虚拟点击间隔仅是
脚本设定的操作耗时，不能作为真实设备速度。

每个 tick 的本地 `tick_profile` 审计事件记录各阶段耗时及扫描复用状态；启用 Jev
时附加分流结果、请求数和 token 计数，不记录会话正文或截图。应先看列表扫描、
会话观察、决策与发送阶段各自占比，再决定下一步优化。

| `stage_ms` 字段 | 当前 TaShuo provider 的工作 |
| --- | --- |
| `scan` | 准备列表、截图、列表视觉模型 |
| `open_thread` | 按锚点进入会话、会话视觉模型、目标与 inbound 证据 |
| `observe_thread` | 复用刚读取的会话，写入本地记忆 |
| `decide` | 可选 Jev 分流、需要时起草与策略检查 |
| `send` | staging、精确文本验证、click checkpoint 与 fresh post-send 验证 |

`scan_reused=true` 表示复用发现队列，`scan` 为 0；不表示跳过会话或发送验证。
`triage.duration_ms` 可用于观察 Jev 给决策阶段增加的成本。未调用的阶段记为 0。

实机运行须处于用户授权的 ManagedRun 窗口，并满足 `AGENTS.md` 的 readiness、
runtime scope 和发送验证条件；源码更新后先完成安装/兼容性检查。代码与离线
测试通过不能替代真实发送验证。

恢复功能接入前的常规离线验证快照为 1856 passed、193 deselected、249 subtests passed，耗时
85.07 秒。随后补充旧 active 状态与未收尾消息组并存的暂停边界，另行通过全部
103 项 ManagedRun 测试与该文件 mypy。16 个相关文件类型检查、最终 Ruff 和 diff
检查通过；这些结果均不代表实机连续发送通过。

### 输入框 IO 的局部计时

实机分段测量发现，旧 capture 的两次 AX 递归合计约 4.915 秒，旧 prepare 的
两次输入框读取合计约 4.819 秒，此外还有重复激活与聚焦操作。新路径只缓存
输入框的结构索引，每次重新读取值、焦点和几何；定位失效时重新发现，不缓存状态。
已在前台且输入框已聚焦时跳过重复操作。

| 阶段 | 旧路径单次测量 | 新路径单次测量 |
| --- | --- | --- |
| capture，首次发现输入框 | 6.605 秒 | 4.761 秒 |
| capture，复用定位路径 | 未单独测量 | 1.917 秒 |

这是 capture/prepare 的局部样本，不含完整决策与发送流程，也不能证明实际发送
